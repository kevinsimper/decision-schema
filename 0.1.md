# Decision Schema 0.1

Status: **Draft** · Published: 2026-10-20 · Author: Kevin Simper

This document defines a shared logical data model for operational evidence, decisions, and work. It is the normative specification. The [examples](examples.md) and [implementation guide](implementation.md) are informative.

## Purpose

Each feature may have its own domain model. Decision Schema standardizes the layer that records what happened, what is believed, what was decided, and what work follows. The same five logical tables MUST serve all participating features within an implementation.

Vehicles, documents, people, bookings, and other domain entities remain in their existing systems of record. Decision Schema does not define their schemas, an agent runtime, an HTTP API, a query language, or an execution engine.

The model separates:

1. An event: a recorded occurrence.
2. Event lines: balanced movements belonging to an event, when applicable.
3. An observation: an assertion supported by evidence, which may be incomplete or wrong.
4. A decision: a judgment with a plan and explicit conditions for review.
5. A task: an assigned unit of work with an execution lifecycle.

These records need not form a linear pipeline. Humans, agents, and deterministic application logic can create them.

## Conventions and shared fields

### Requirement language

MUST and MUST NOT identify requirements for conformance. SHOULD and SHOULD NOT identify recommendations that may have documented exceptions. MAY identifies an option.

### Logical representation

The names below are the canonical names for the logical model. Physical columns, indexes, normalized relationship tables, JSON storage, and partitions MAY differ, provided an implementation documents its mapping and preserves these semantics. The five tables describe five logical record kinds, not a limit on physical tables or infrastructure.

All fields listed as required MUST be present and non-null. Optional fields MAY be omitted or null; optional lists default to empty lists. Unknown extension fields MUST NOT redefine the meaning of a standard field.

| Type        | Meaning                                                                                                                                        |
| ----------- | ---------------------------------------------------------------------------------------------------------------------------------------------- |
| ID          | Nonempty, opaque, case-sensitive string, unique within its logical table and scope. Never reused.                                              |
| Reference   | Nonempty, stable, case-sensitive string identifying an entity within a scope, for example `vehicle:v-4318`.                                    |
| Timestamp   | An instant represented as an RFC 3339 string in UTC, using `Z`; native storage MAY differ.                                                     |
| Type name   | Nonempty, case-sensitive string with a documented meaning and payload contract; namespaced names such as `insurance.uploaded` are RECOMMENDED. |
| JSON object | An object containing documented, type-specific data. An empty object is valid.                                                                 |

Sorting or comparison of timestamps MUST compare instants, not assume all permitted timestamp strings sort chronologically as text. An implementation MAY require a canonical precision for storage.

### Common record fields

Every row in all five tables MUST provide these fields:

| Field         | Type      | Meaning                                                              |
| ------------- | --------- | -------------------------------------------------------------------- |
| `id`          | ID        | Record identity.                                                     |
| `scope_id`    | Reference | Ownership and access boundary, such as an organization or workspace. |
| `subject_ref` | Reference | The primary entity this record concerns.                             |
| `recorded_at` | Timestamp | When the application durably recorded this row.                      |
| `recorded_by` | Reference | The human, agent, or system that recorded it.                        |

The same entity MUST use the same reference across features in the same scope. References MUST remain stable when a name, registration number, or external label changes. An integration MUST resolve aliases before writing records intended to refer to the same subject.

Record-to-record references below identify the target table and ID implicitly through their field, except `evidence_refs`, which carries both. All linked records MUST exist in the same scope. Domain references MUST resolve to entities or documented reserved accounts in that scope. Implementations MUST validate these relationships and enforce authorization on reads and writes. A reference does not grant access.

### Evidence

An `evidence_refs` list contains objects of this exact shape:

```json
[
  { "table": "events", "id": "e-1" },
  { "table": "observations", "id": "o-1" }
]
```

The allowed target tables are `events` and `observations`. Evidence MAY concern another subject within the same scope. References MUST be inspectable by authorized readers, subject to source permissions. An assertion does not become a verified fact merely because another record cites it.

### Extensions

Each implementation MUST document its event, observation, decision, and task types, their payload contracts, and domain validation. Payloads MAY contain domain references, but an implementation MUST NOT hide required standard relationships or lifecycle fields exclusively inside payloads.

## Events

An event records something that occurred, such as a document upload, a customer report, or a completed inspection. A report event establishes that the report was received; it does not establish that its contents are true.

In addition to the common fields:

| Field                  | Type           | Required | Meaning                                                               |
| ---------------------- | -------------- | -------- | --------------------------------------------------------------------- |
| `event_type`           | Type name      | Yes      | What happened.                                                        |
| `occurred_at`          | Timestamp      | Yes      | When it happened, distinct from recording time.                       |
| `summary`              | String         | Yes      | Nonempty human-readable description.                                  |
| `payload`              | JSON object    | Yes      | Event-specific data, including provenance where applicable.           |
| `related_subject_refs` | Reference list | No       | Additional subjects explicitly connected to this event.               |
| `source_ref`           | Reference      | No       | Stable source record, such as a message, document, or external event. |
| `corrects_event_id`    | ID             | No       | Earlier event being corrected by this event.                          |

Events MUST be append-only in ordinary operation. Corrections MUST record an additional event and preserve the original. Correction handling MUST be documented; a correction does not silently reverse ledger entries or previous decisions. A movement correction requires compensating movement lines.

Integrations MUST prevent replay of the same source occurrence from creating duplicate business events. Distinct occurrences MUST remain distinguishable even when they have identical payloads or timestamps. The deduplication key is implementation-specific.

## Event lines

An event line records one side of a movement of quantity, ownership, custody, or responsibility. Events without movements have zero lines. All lines of a movement MUST be committed atomically with their event.

In addition to the common fields:

| Field          | Type           | Required | Meaning                                                                                    |
| -------------- | -------------- | -------- | ------------------------------------------------------------------------------------------ |
| `event_id`     | ID             | Yes      | Parent row in `events`.                                                                    |
| `account_ref`  | Reference      | Yes      | Location, owner, custodian, or responsibility account receiving or giving up the resource. |
| `resource_ref` | Reference      | Yes      | Resource being moved, such as a serialized printer or a stock item.                        |
| `quantity`     | Decimal string | Yes      | Nonzero signed quantity: positive receives, negative gives up.                             |
| `unit`         | String         | Yes      | Nonempty documented unit, such as `item`.                                                  |

The line's `scope_id` and `subject_ref` MUST match its parent event. For every `(scope_id, event_id, resource_ref, unit)` group, quantities MUST sum to exactly zero using exact arithmetic. Decimal strings use a leading minus for negatives, digits, and an optional decimal point with fractional digits; exponent notation, a leading plus, and binary floating-point arithmetic are not permitted.

Movements into or out of the tracked system MUST use explicit documented boundary accounts, such as `account:external` or `account:retired`. A zero sum establishes balance, not sufficient stock, correct ownership, or permission to move an item; domain rules MUST enforce those separately.

Lines MUST be append-only in ordinary operation. A correction uses a new event with compensating lines. Current balances are derived from the ledger; snapshots MAY accelerate reads but MUST be rebuildable.

## Observations

An observation records a claim, report, assessment, or interpretation. It preserves who recorded it and the evidence supporting it. Conflicting observations MAY coexist.

In addition to the common fields:

| Field                       | Type          | Required | Meaning                                                                               |
| --------------------------- | ------------- | -------- | ------------------------------------------------------------------------------------- |
| `observation_type`          | Type name     | Yes      | Kind of assertion.                                                                    |
| `observed_at`               | Timestamp     | Yes      | When the underlying assessment or report applies.                                     |
| `assertion`                 | String        | Yes      | Nonempty statement of what is believed or being withdrawn.                            |
| `state`                     | Enum          | Yes      | `asserted` or `withdrawn`.                                                            |
| `evidence_refs`             | Evidence list | Yes      | Supporting events or earlier observations; MAY be empty when no support is available. |
| `payload`                   | JSON object   | Yes      | Observation-specific data.                                                            |
| `supersedes_observation_id` | ID            | No       | Previous observation replaced or withdrawn.                                           |

Observation contents MUST be append-only in ordinary operation. Replacement or withdrawal MUST append a new observation. A successor MUST have the same scope, subject, and observation type as its predecessor, and a predecessor MUST have at most one direct successor. Cycles are forbidden. A `withdrawn` row MUST supersede an observation and explain the withdrawal in `assertion`.

A current observation is a row with `state = asserted` and no successor. Independent assertions MUST NOT supersede each other merely because they have the same type. Applications MUST preserve relevant conflicting assertions rather than silently select the most recently recorded claim as truth.

Evidence links MUST NOT create cycles between observations. Lack of an observation MUST NOT be interpreted as evidence that a condition is false.

## Decisions

A decision records a conclusion, its supporting business rationale, and a plan. The plan may be to act, wait, or consider a concern resolved. Rationale is an inspectable explanation of the judgment; private model reasoning traces are not required.

In addition to the common fields:

| Field                    | Type           | Required | Meaning                                                                             |
| ------------------------ | -------------- | -------- | ----------------------------------------------------------------------------------- |
| `decision_type`          | Type name      | Yes      | Kind of judgment and its payload contract.                                          |
| `concern`                | String         | Yes      | Nonempty, documented key distinguishing independent decisions for the same subject. |
| `outcome`                | Enum           | Yes      | `act`, `wait`, or `resolved`.                                                       |
| `conclusion`             | String         | Yes      | Nonempty statement of the judgment.                                                 |
| `rationale`              | String         | Yes      | Nonempty explanation sufficient to inspect why it was chosen.                       |
| `plan`                   | String         | Yes      | Nonempty description of intended action, waiting, or resolution.                    |
| `evidence_refs`          | Evidence list  | Yes      | Evidence used; MAY be empty, with limitations explained in the rationale.           |
| `payload`                | JSON object    | Yes      | Decision-specific data.                                                             |
| `review_at`              | Timestamp      | No       | Time at which review becomes due.                                                   |
| `review_on_event_types`  | Type name list | No       | Event types that make this decision due for review.                                 |
| `supersedes_decision_id` | ID             | No       | Previous decision for this subject and concern.                                     |

`(scope_id, subject_ref, concern)` identifies one decision chain. `concern` MUST distinguish concurrent concerns, such as `insurance` and `fuel-inspection`; there is no single global “current decision” for a vehicle. Implementations MUST document concern keys and their meaning.

Each chain MUST have exactly one root and at most one successor per decision. Successors MUST preserve scope, subject, and concern. The decision type MAY change. Cycles and forks are forbidden, including under concurrent writes. The current decision is the row with no successor.

Decision contents MUST NOT be edited during ordinary operation. Reevaluation appends a new decision, including when the conclusion is reaffirmed. The successor MUST identify its predecessor and explain the renewed judgment. Original timestamps and review conditions MUST remain available.

An `act` or `wait` decision MUST have at least one review condition: `review_at` or a nonempty `review_on_event_types`. A `resolved` decision MAY have neither, or MAY retain conditions under which the concern should be reopened. An implementation SHOULD use a scheduled fallback when an expected event might never arrive.

Being due for review does not supersede or expire a decision. The current decision and its overdue or event-triggered review state MUST remain visible until a successor is recorded. A decision does not itself prove that an action was executed.

## Tasks

A task is a unit of executable work assigned to a human or agent. It may be created from a decision or directly by an authorized user or system.

In addition to the common fields:

| Field             | Type        | Required | Meaning                                                          |
| ----------------- | ----------- | -------- | ---------------------------------------------------------------- |
| `task_type`       | Type name   | Yes      | Kind of work and its payload contract.                           |
| `title`           | String      | Yes      | Nonempty description of work.                                    |
| `status`          | Enum        | Yes      | `pending`, `in_progress`, `completed`, `failed`, or `cancelled`. |
| `assignee_ref`    | Reference   | Yes      | Responsible person, agent, or documented work queue.             |
| `payload`         | JSON object | Yes      | Task-specific inputs.                                            |
| `updated_at`      | Timestamp   | Yes      | Last task mutation; initially equal to `recorded_at`.            |
| `decision_id`     | ID          | No       | Decision authorizing or motivating this work.                    |
| `due_at`          | Timestamp   | No       | When the task is due.                                            |
| `result_event_id` | ID          | No       | Event recording the result.                                      |
| `status_reason`   | String      | No       | Explanation of failure, cancellation, or another status change.  |

A task MAY concern a different subject from its decision, within the same scope: a vehicle decision can create a booking task. Task state and assignment MAY be updated. `recorded_at` and `recorded_by` MUST continue to identify initial creation.

Allowed status transitions are `pending → in_progress`, `pending → cancelled`, and `in_progress → completed | failed | cancelled`. Terminal tasks MUST NOT be reopened; retrying a failed or cancelled task creates a new task. Implementations MUST preserve an inspectable history of task status transitions, for example through events. Marking a task `completed` MUST link a result event describing the actual outcome. Failed or cancelled tasks MUST have a nonempty status reason.

Before an external side effect, an executor MUST check current authorization, domain preconditions, and whether a linked decision is still current and supports the work. A task linked to a superseded decision MUST NOT execute as if still authorized by that decision. Pending tasks MUST be cancelled with a reason or replaced under the new decision. For work already in progress, implementations MUST document how they reconcile completion, interruption, or compensation. Completed work remains historical fact.

An event-triggered review MUST be considered during this check: if relevant new evidence could invalidate the action, the executor MUST resolve that review before proceeding. Lease management, delivery retries, and outboxes are implementation concerns; task status alone does not guarantee exactly-once effects.

## Reevaluation

### Scheduled review

A current decision is due for scheduled review when `review_at` is non-null and is less than or equal to the current time. Review times are instants; local schedules MUST be converted using the intended time zone before recording them.

### Event-triggered review

An event matches a decision's review conditions when:

1. Its scope matches the decision's scope.
2. Its type is in `review_on_event_types`.
3. The decision's subject is the event's primary subject or one of its `related_subject_refs`.
4. The event was durably recorded after that decision.

Implementations MUST preserve a deterministic recording order for this purpose, including equal timestamp values. Timestamps alone are insufficient: an implementation MAY use commit order, a sequence, or a transaction boundary in addition to the logical fields. Late-arriving events MUST be matched by their recording order, rather than excluded because their occurrence time is old.

A matching event makes the current decision due for review. It does not modify the conclusion, create an automatic task, or authorize a side effect. Implementations MAY support additional documented trigger predicates, but MUST support the base matching rule without requiring them.

### Recording a review

A review MUST read the current decision and relevant evidence, then append a successor against that exact decision. A concurrent replacement MUST cause the stale write to be rejected or retried after reloading the chain. New evidence arriving during review MUST remain eligible to trigger review of the resulting decision if it was not included in the reviewed context; it MUST NOT be silently acknowledged by the later decision timestamp.

Implementations MUST durably track pending review work or be able to reconstruct it, and MUST tolerate event redelivery without creating duplicate decisions or duplicate actions. Trigger bookkeeping is infrastructure and need not add a sixth logical domain concept. Event identifiers or a recording-order watermark SHOULD accompany review context. A failed review MUST leave the need for review visible and retryable.

## Conformance

An implementation claiming **Decision Schema 0.1 draft conformance** MUST:

- Expose the five logical record kinds and document their physical mapping, type vocabulary, concern keys, and domain references.
- Preserve the fields, relationships, current-record rules, and lifecycle requirements in this document.
- Support both scheduled and base event-triggered review, including late arrivals, concurrent reviews, and evidence arriving during a review.
- Enforce scope boundaries and source permissions, and preserve task justification before execution.
- Validate the [acceptance scenarios](examples.md#acceptance-scenarios).

An implementation MAY have no event lines until its first movement. An implementation adopting only part of the model SHOULD describe itself as a partial adoption and list unsupported requirements rather than claim full conformance.

Append-only requirements describe ordinary application behavior. An implementation MUST separately document retention, deletion, and redaction policies, including the effect on references and derived views. It MUST NOT use those administrative policies to silently rewrite decision history during normal operation.

This is a draft proposal, not a certification program. SQL dialects, APIs, agent frameworks, and specific model providers are outside its contract.
